# OpenShift ZTP: ACM Hub -> Assisted Installer -> Spoke GitOps

This repository deploys OpenShift cluster **`ove604a.walelab.smoad.net`** from the ACM Hub with Argo CD, Assisted Installer, BareMetalHost, NMState, HashiCorp Vault Secrets Operator, and spoke-side OpenShift GitOps.

## Ownership model

```text
ACM HUB
  |
  | Hub Argo CD / ApplicationSet
  v
ove604a namespace
  |
  |-- VaultConnection + VaultAuth
  |-- VaultStaticSecret #1: pull-secret
  |-- VaultStaticSecret #2: bmc-credentials
  |-- VaultStaticSecret #3: vault-bootstrap-credentials
  |-- ClusterDeployment / AgentClusterInstall / InfraEnv
  |-- BareMetalHosts / NMStateConfig
  |-- ConfigMap/day2-bootstrap (extra manifests)
  `-- Job/vault-bootstrap
           |
           | waits for AgentClusterInstall Completed=True
           | reads spoke admin kubeconfig
           | configures Vault JWKS/JWT trust
           v
       Vault
         jwt-ove604a
         role:   ove604a-day2
         policy: ove604a-day2
           |
           v
SPOKE ove604a
  |
  | Extra manifests install:
  |-- OpenShift GitOps Operator
  |-- Vault Secrets Operator
  |-- day2-bootstrap RBAC/Job
  |
  | day2-bootstrap Job waits for operator CRDs
  |-- creates ServiceAccount/day2-vault
  |-- creates VaultConnection/day2-vault
  |-- creates VaultAuth/day2-vault-auth -> jwt-ove604a
  |-- creates VaultStaticSecret #4 -> cluster-config-repository
  `-- creates Application/ove604a-cluster-config
           |
           v
      Day-2 config repo
```

## Why the Day-2 resources are created by a Job

The extra-manifest bundle installs the GitOps and Vault Secrets Operators first. GitOps is installed in the dedicated `openshift-gitops-operator` namespace with an explicit `OperatorGroup`, using `redhat-operators` on `latest`; Vault Secrets Operator is subscribed from `certified-operators` on `stable` in `openshift-operators`. Their CRDs do not necessarily exist at the instant the installer applies the extra manifests. Creating `VaultAuth`, `VaultStaticSecret`, or `Application` directly in the same bundle can therefore race the operator CRD installation.

`13-day2-bootstrap-job.yaml` waits until these CRDs exist and only then creates the dependent resources.

## Four VaultStaticSecrets

Exactly **four** are required by this solution:

| Where | VaultStaticSecret | Vault path | Kubernetes Secret |
| --- | --- | --- | --- |
| Hub | `pull-secret` | `acm/ove604a/pull-secret` | `pull-secret` |
| Hub | `bmc-credentials` | `acm/ove604a/bmc` | `bmc-credentials` |
| Hub | `vault-bootstrap-credentials` | `acm/ove604a/vault-bootstrap` | `vault-bootstrap-credentials` |

## Kustomize patch naming

The overlay uses normal YAML files under `patches:`. It does **not** use JSON6902 `op: replace`. Because OpenShift 4.20 `oc` embeds Kustomize 5.6.x, the overlay uses Kustomize `replacements` only for final `metadata.name` values. Cluster resources take the name from `Namespace/ove604a`; each BareMetalHost takes its object name from the hostname annotation already set by its YAML patch.

The overlay intentionally does **not** set a global Kustomize `namespace:` transformer. `ManagedCluster` is cluster-scoped, and Hub RoleBinding subject namespaces also need to stay explicit. Normal YAML patches therefore set `ove604a` only on namespaced Hub resources.

## Cluster-specific Vault endpoint

For `ove604a`, Vault is configured as:

```text
http://192.168.1.123:8200
```

The value is intentionally kept out of the reusable base and out of Vault secret data. It is set only in the cluster overlay:

- `overlays/cluster/acm/acm704a/ove604a/provisioning-vault-connection-patch.yaml` — Hub VSO connection.
- `overlays/cluster/acm/acm704a/ove604a/day2-bootstrap-configmap-patch.yaml` — injects `ConfigMap/day2-site-config` into the spoke extra-manifest bundle.

The Hub `vault-bootstrap` Job reads the endpoint from `VaultConnection/provisioning-vault`; its VaultStaticSecret only supplies `VAULT_TOKEN`. The spoke `day2-bootstrap` Job reads the endpoint from `ConfigMap/day2-site-config`.

## Values still required before deployment

There are three remaining categories of deployment-specific values to verify before deployment:

1. Replace `<YOUR_SSH_PUBLIC_KEY>` in the `ove604a` overlay patches (or the base).
2. Replace each `CHANGE_ME_ENS224_MAC_*` in `overlays/cluster/acm/acm704a/ove604a/nmstate/` with the actual **ens224** MAC. Do not reuse the BMH boot MAC unless ens224 is actually the boot NIC.
3. For this 3-control-plane HA cluster, confirm the API/Ingress VIP design. If Assisted Installer is managing the VIPs, uncomment and set `apiVIP` and `ingressVIP` in `agentclusterinstall-patch.yaml` (and add `networking.machineNetwork` if required for your topology). If you use user-managed networking/external load balancing, keep them external and validate that design before sync.

The NMState schema is already corrected: static configuration is under `spec.config.interfaces`, while `spec.interfaces[].macAddress` identifies which physical host/interface receives that configuration.

## Vault setup

The Hub already requires Vault Secrets Operator to be installed before this repository is synchronized.

The Hub provisioning `VaultAuth` uses the per-cluster Vault role:

```text
ove604a-provisioning
```

The post-install Hub Job then creates the dedicated spoke JWT mount:

```text
jwt-ove604a
```

It configures that mount against the spoke API JWKS endpoint, creates `ove604a-day2`, and binds it to:

```text
system:serviceaccount:openshift-gitops:day2-vault
```

This avoids sharing one JWT verifier/identity namespace across all spoke clusters. Vault must be able to resolve and reach the spoke API/JWKS endpoint after installation. See `docs/vault-prerequisites.md` for the Hub Kubernetes-auth prerequisite, bootstrap-token scope, network reachability, and TLS notes.

## Day-2 Git repository secret

Vault path:

```text
acm/ove604a/day2/git
```

must contain at least:

```text
url=<Git repository URL>
```

and the authentication fields required by that repository (`username`/`password` or `sshPrivateKey`). VSO creates the Argo CD repository Secret with the required `argocd.argoproj.io/secret-type: repository` label.

The bootstrap Job creates the local Argo Application with:

```text
path: overlays/ove604a
```

Change `DAY2_REPO_PATH_PREFIX` in `13-day2-bootstrap-job.yaml` if the Day-2 repository uses a different directory layout.

## Hub deployment

Apply the ApplicationSet once on the ACM Hub:

```bash
oc apply -f ztp-install/argo/appset-argo.yaml
```

It discovers cluster overlays under:

```text
ztp-install/overlays/cluster/acm/*/*
```

For direct testing without ApplicationSet:

```bash
oc apply -k ztp-install/overlays/cluster/acm/acm704a/ove604a
```
